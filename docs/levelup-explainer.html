Project explainer

LevelUp: a career operating system for engineering students

A full-stack web app that takes a B.Tech student from “I don’t know what to prepare” to “placement-ready”. It includes AI resume review, voice mock interviews and personal roadmaps. Every one of those activities produces data, and faculty use that data to spot students who are falling behind while there is still time to help.

12features across two user groups
5roles: student, faculty, HOD, principal, placement
27MongoDB collections
14REST route groups + Socket.io
Why this exists

The problem, from both sides of the classroom

Placement preparation is split across a dozen tools, and none of them talk to each other. The student can’t see their own progress, and the college can’t see it either.

Student

Preparation with no plan

Hours spent across YouTube, coaching sites and practice portals, with no record of what was studied, how well, or what’s missing.

Student

Rejected by a machine

Many resumes are filtered out by an ATS before a person reads them, and the student never finds out why.

Student

Little interview practice

Mock interviews are rare, expensive or both, so the first real interview is often the first time a student answers out loud.

Faculty & HOD

Problems found too late

Marks, attendance, arrears and placement data sit in separate Excel files. An at-risk student usually shows up only after the exam results.

The one idea to remember

Every student action becomes a signal

The features are not a random list. Each student feature produces data. The data is combined into one readiness score. The score, together with attendance and assignment records, tells faculty exactly who needs help and why. This loop is the core of the project.

How it is built

Architecture

A layered MERN application. The browser does as much work as it safely can (speech, video, PDF export). The server handles everything that needs trust: grading, scoring, access control and AI calls.

One request, end to end: uploading a resume

  1. The browser sends the PDF as multipart form data, with the JWT in the Authorization header.client/src/pages/ResumeAnalysis.jsx
  2. Gateway checks: security headers, CORS, then the rate limiter (10 analyses per hour per IP, because each call costs money), then protect verifies the token and loads the user.server/app.js · server/middleware/auth.js
  3. Multer keeps the file in memory. Nothing touches the disk, which also works on serverless hosts.server/routes/resume.js
  4. pdf-parse extracts the text. If there are fewer than 30 characters, the PDF is probably scanned, so it is rejected straight away with a helpful message.
  5. aiService sends the text to LLaMA 3.3 via Groq, validates the JSON with Zod, and uses a rule-based scorer if the AI fails.server/services/aiService.js
  6. Cloudinary stores the file. If that upload fails, the request still succeeds, because storage is not the critical part.
  7. MongoDB saves the analysis and moves the previous score into versions[], so progress is visible over time.
  8. The response returns the score, 5 dimension breakdowns and tips, and React renders them.

Deployment

Vercel: frontend and REST API

  • The React build is served as static files from a CDN
  • The Express API runs as serverless functions through api/index.js
  • The Mongoose connection is cached between calls, so each request doesn’t reconnect

Persistent host (Render/Railway): real-time

  • Socket.io: live grid, focus heartbeats, WebRTC signaling, course chat
  • node-cron: nightly analytics aggregation
  • Needed because serverless functions can’t hold open connections

Features for students

F1 · student

AI Resume Analyzer

Show students why their resume would be rejected, and how to fix it, before a company’s filter rejects it.

How it works
  1. The student uploads a PDF and can add a target job title and company.
  2. The server extracts the text with pdf-parse. Scanned or image-only PDFs are rejected with a clear message.
  3. The text goes to LLaMA 3.3, prompted to act as a strict recruiter (“70 = decent, below 50 = instant reject”) and to support every score with evidence from the resume.
  4. The AI scores 5 dimensions, each with 3–5 tips: Tone & Style, Content, Structure, Skills (with detected skills) and ATS (with keywords to add).
  5. The result is saved. The previous score moves into version history, so the student can see improvement across uploads.
Under the hood
Endpoint
POST /api/resume/upload
Libraries
Multer (memory), pdf-parse, Groq SDK, Zod, Cloudinary
Rate limit
10 analyses per hour per IP
Code
server/routes/resume.js, server/services/aiService.js
Fallback scorer used when the AI is unavailable (out of 100)
CheckMaxHow
Technical skills304 points per skill found in a skills dictionary
Sections present20Education, Projects, Experience…
Action verbs15“developed”, “led”, “optimised”: 2.5 each
Quantified results10numbers and percentages present

Design decision

Treat AI output as untrusted input. A language model can return broken JSON or a missing field. Every field is checked with a Zod schema that has safe defaults (.catch(50)), so a bad AI response never crashes the page.

Only fail on the critical path. If Cloudinary is down, the student still gets the analysis. Extracting, analysing and saving must succeed; storing the file is optional.

A real PDF parser, an LLM acting as a strict recruiter, a schema check on its answer, and a rule-based backup, so the feature never goes down.

F2 · student

Resume Builder

For students who don’t have a resume yet: build one by chatting, then download it as a PDF.

How it works
  1. Manual mode: a form for personal details, summary, skills, experience, projects, education, certifications and achievements, with add/remove for each list.
  2. AI chat mode: the student describes themselves in plain language. The AI returns a structured resume. It writes a 2–3 line summary, rewrites bullets as “Developed X using Y, resulting in Z”, and groups skills into 7 buckets.
  3. Save draft to MongoDB and continue later.
  4. Export PDF (A4) generated entirely in the browser with jsPDF.
Under the hood
Endpoints
POST /api/resume/ai-build, /save-draft, GET /draft
Skill buckets
languages, frontend, backend, ai, databases, tools, concepts
Code
client/src/pages/ResumeBuilder.jsx
Design decision

Generate the PDF on the client. Server-side PDF rendering needs a headless browser, which is heavy and slow. jsPDF in the browser costs the server nothing and the download is instant.

An honesty rule in the prompt: the AI is told to “use reasonable defaults but DO NOT fabricate facts.” A resume builder that makes up experience would hurt the student.

Chat with the AI, get an ATS-friendly resume, download it, then score it with the Analyzer. The two features work as a pair.

F3 · student

AI Mock Interviews

Realistic interview practice, spoken aloud, available at 2 a.m. the night before the drive.

How it works
  1. The student picks one of 9 tracks: Behavioral (STAR method), Java, Python, DSA, MERN, OS, DBMS, Computer Networks, or Project Demo, where they describe their own project and the AI asks about its architecture.
  2. The AI’s question is read aloud (speechSynthesis). The student answers by speaking, and SpeechRecognition turns it into text.
  3. Each answer is sent with the conversation so far. The AI returns feedback, a model answer (100–200 words) and a harder next question.
  4. After 15 questions it gives a performance summary.
  5. The session is saved and also logged as study activity, so it counts toward analytics and readiness.
Under the hood
Endpoints
POST /api/chat (each turn), POST /api/interview/session (save)
Voice
Browser Web Speech API, so no audio is uploaded
Fallback
Built-in question bank with hints and expected keywords. Answers are graded by how many keywords they cover.
Code
InterviewLobby.jsx, server/services/chatService.js
Design decision

Speech stays in the browser. Speech-to-text runs on the device, so only text reaches the server. That makes it free, fast and private, since the student’s voice is never stored. The trade-off: the Web Speech API works best in Chrome and Edge.

A stateless server. The client sends the history with every turn, so any server instance can answer any request. That is why this works on serverless hosting.

Speak your answer, get feedback and a model answer, then face a harder question. Like a senior engineer interviewing you, on demand.

F4 · student

Peer Video Rooms

When AI practice isn’t enough: a face-to-face mock interview with a classmate or senior.

How it works
  1. One student creates a room and shares its ID. The other joins.
  2. Both browsers connect to Socket.io and swap connection details. This is called signaling: offer → answer → ice-candidate.
  3. Google STUN servers tell each browser its public address, so they can find each other through home or college routers.
  4. Once connected, video and audio flow directly between the two browsers.
  5. A third person trying to join gets “room full”.
Under the hood
Events
join-room, offer, answer, ice-candidate, user-disconnected
Capacity
2 people per room
Code
InterviewRoom.jsx, server/server.js
Design decision

The server only introduces the two browsers. A media server that relays video costs bandwidth for every minute of every call. Peer-to-peer makes the video cost about zero. The limit of 2 people keeps it a simple one-to-one connection.

Known limit: there is only STUN, no TURN relay. On very strict networks (some college firewalls) a direct connection can fail. Adding a TURN server is the fix, and it is on the roadmap.

Our server only introduces the two browsers. After that, the video goes directly between them.

F5 · student

Career Roadmap

Answers “what should I study, and in what order?” based on where the student is today.

How it works
  1. The student sets a target role, a timeline in months, their experience level, goals and a target company type.
  2. The server adds data it already has: skills from the resume, the resume score and quiz averages from the modules.
  3. The AI changes its advice by company type (table below).
  4. The output has month-by-month phases with priorities, a Monday–Sunday timetable, a gap analysis, portfolio project ideas, resources and interview focus topics.
  5. It is saved, and students tick off tasks as they go.

Give the AI real data, not just the form. An AI that sees only “target: SDE” gives generic advice. Adding the student’s actual resume skills and quiz scores makes the plan personal. This is called context engineering.

F6 · student

Learning Modules & Quizzes

Structured learning, a code runner and exam-style tests in one place.

How it works
  1. 18+ modules: Java, Python, JavaScript, TypeScript, C, C++, Go, Rust, DSA, System Design, SQL, MongoDB, Docker/Kubernetes, AWS, GenAI, ML, Deep Learning and Logical Reasoning.
  2. Completing a lesson updates the student’s progress. An AI tutor answers questions about the current lesson.
  3. Code runner: JavaScript runs on the server in a sandbox with a 1.5-second timeout, so an infinite loop can’t freeze the server.
  4. Quiz anti-cheating: switching tabs gives a warning, and 3 warnings auto-submit the quiz. Copy and paste can be blocked. Every violation is recorded with a timestamp.
  5. Grading happens on the server. The correct answers are never sent to the browser.
Under the hood
Endpoints
/api/modules/:slug, /quiz/:id/submit, /execute
Sandbox
Node vm context with only console.log exposed
Code
server/routes/modules.js, QuizPage.jsx
Design decision

Never trust the client. If correct answers were sent to the browser, anyone could open DevTools and read them. The browser sends only the student’s choices, and the server grades them.

Being honest about the sandbox: Node’s vm blocks infinite loops but is not a full security boundary. In production, untrusted code should run in an isolated container (Docker or a judge service like Judge0). Knowing where your own system is weak is what reviewers look for.

Learn, run code and take a test in one place, with anti-cheating and grading the browser can’t fake.

F7 · student

Language Hub

Communication practice through roleplay, such as a German tech interview in Berlin, with a native-speaker AI.

How it works
  1. The student picks a language and a real-life scenario.
  2. The AI plays a native speaker and replies only in that language, in 1–2 natural sentences.
  3. If the student makes a real grammar or vocabulary mistake, the AI adds a hidden [GRAMMAR_FEEDBACK] block at the end of its reply.
  4. The server splits that block off, so the conversation stays in character and the correction appears as a separate English card.
  5. XP points and lesson progress are saved, Duolingo-style.
Under the hood
Endpoint
POST /api/language/roleplay
Stored in
LanguageProfile: XP, current language, lesson progress
Code
server/controllers/languageController.js
Design decision

One AI call, two outputs. A separate “grammar checker” call would double the cost and the wait. Asking the model to append a marked block and splitting it on the server gives both the reply and the correction in one call.

The chat history is cleaned down to role and content before it goes to the AI, so extra fields from the client can’t leak into the prompt.

Roleplay with a native speaker who quietly corrects your grammar without breaking the conversation.

F8 · student

Study Analytics & Focus Tracking

Measures actual study, not just time logged in, and shows it back to the student.

How it works
  1. The browser watches mouse, keyboard, scroll and touch. 2 minutes with no input counts as idle. Tab switches are caught with visibilitychange.
  2. Every 30 seconds a heartbeat is sent over Socket.io. 90 seconds without one means the session was abandoned (for example, the laptop was closed).
  3. Session state is kept in server memory and written to MongoDB in batches every 60 seconds.
  4. At the end of a session a Focus Score is calculated (see Scoring models).
  5. The dashboard shows study hours, streaks, quiz trends, category breakdowns and a focus-score ring.
Under the hood
Socket events
session:start, :heartbeat, :idle, :resume, :tab-switch, :end
Privacy
Only records whether the student interacted, never what they typed. No camera.
Code
ActivityContext.jsx, server/services/sessionManager.js
Design decision

Batch the writes. Writing every heartbeat for every student would put a heavy, constant load on the database. Collecting updates in memory and writing once a minute cuts that sharply.

The trade-off: in-memory state means one server process owns the sessions. To scale out to several servers, that state would move to Redis, and Socket.io would use its Redis adapter.

It measures whether you were actually focused, not whether the tab was open. The same data then drives the teacher’s live view.

F9 · faculty

“Ask AI” Analytics

Faculty ask questions in plain English and get a chart, with no database queries to write.

How it works
  1. A teacher types something like “Who are the top 5 students?” or “Show at-risk students this week.”
  2. A rule-based language matcher compares the question against 10 patterns and picks out the time range (today, week, last month…).
  3. The matched pattern runs a fixed MongoDB aggregation, limited to the teacher’s own classrooms.
  4. The result comes back with a display type (line, bar, radar or pie chart, a table, or stat cards) and React renders it.
The 10 patterns
Performance
study time · quiz scores · resume scores · top performers
Attention
at-risk · attendance · trends
Summary
overview · compare · category breakdown
Code
server/services/analyticsQueryEngine.js
Design decision

We deliberately did not let an LLM write the database queries. For a college’s data, an answer must be correct, not just plausible. Fixed, tested queries mean the numbers are never invented, the response is instant and costs nothing, and there is no way for the AI to be tricked into reading another department’s data.

The trade-off: it understands only phrasings that match its patterns. The next step would be an LLM that classifies the question into one of the 10 intents, while the queries themselves stay fixed.

Faculty ask in English and get a chart. We chose accuracy over flexibility, because an analytics tool must never make up a number.

F11 · HOD

HOD Department Console

One register for the whole department, replacing a folder of Excel files.

How it works
  1. A register table of every student: USN, roll number, proctor, CGPA, attendance %, arrears and placement status. It can be sorted and searched.
  2. One-click filters: short of attendance, close to the line, arrears pending, placement eligible, merit list.

“Lectures to recover”: classes a defaulter must attend in a row to reach 75%
needed = ⌈ (0.75 × held − attended) ÷ (1 − 0.75) ⌉

Why: after n more classes, all attended, the ratio is (attended + n) ÷ (held + n). Set that ≥ 0.75 and solve for n. Try it in the calculator under Scoring models.

Design decision

F12 · HOD

Excel Workflow: export, edit, import, archive

Colleges run on Excel, so LevelUp works with it and adds safety around it.

How it works
  1. Export the full register or only the filtered view as a 7-sheet workbook: Summary, Register, Attendance, IA Marks, Arrears, Placement, Remarks. The Summary sheet records who made it, when, and a checksum.
  2. Shortage notice in the exam-cell format: shortfall, classes needed, proctor, parent phone and a signature line.
  3. Import, step 1 (preview): the file is compared with the database, showing new students, changed fields before → after, unchanged rows and missing students. Nothing is saved yet.
  4. Import, step 2 (commit): changes are saved only after someone confirms.
  5. Archive: old detail is moved out to a workbook and removed from the database. Re-uploading that workbook restores it.
Safety rules
Matching
by USN, then enrolment ID, then email
Never deletes
students missing from the file are left alone. Remarks are added, never overwritten.
Errors
reported by sheet and row: “attended > held”, “IA > max”, “duplicate USN”
Derived columns
status, % and eligibility are recalculated, so editing them has no effect
Design decision

One column specification drives both export and import. A column can’t be added to the export and forgotten on the way back in (workbookService.js).

Preview, then commit. The same plan-then-apply pattern that infrastructure tools use: a human sees exactly what will change before anything is written.

Archive order matters: build the workbook, then send it, then prune, then write a ledger entry. Nothing is removed from the database until a copy exists somewhere else. Detailed history is about 62% of each student record’s size, so archiving saves real space.

Teachers keep using Excel. LevelUp adds validation, a preview before anything changes, and a safe archive.

The fairness rule

If a student has no data for a part (for example, no mock interview yet), that part is left out and the other weights are rescaled. A new student isn’t punished with zeros for things they haven’t tried.

score = Σ(value × weight) ÷ Σ(weights present)

This used to be calculated in three places with three slightly different results. It now lives in one file, readinessService.js, and every screen uses it.

Defense in depth

Security & reliability

No single check is trusted to do everything. Each layer assumes the one before it might fail.

Identity & access

  • Passwords hashed with bcrypt, never stored in plain text
  • JWT sessions (7-day expiry) checked by protect
  • Role-based access with authorize('hod', …) on every sensitive route
  • Data scoping: scopeData, authorizeClassroom and canAccessStudent. A valid role is not enough, it must also be your class.
  • Demo logins are read-only: any write returns 403 DEMO_READ_ONLY

Input & abuse

  • Helmet security headers and a strict CORS origin
  • Mongo sanitise blocks $-operator injection
  • Rate limits: 500 requests per 15 min overall, 10 resume analyses per hour, and a separate AI limiter
  • Zod validation on inputs and on AI output
  • A 10 MB body limit and a 1.5 s code-execution timeout

Graceful degradation

  • Every AI feature has a rule-based fallback: resume scorer, question bank, template roadmap
  • Non-critical services (Cloudinary) can fail without failing the request
  • Abandoned sessions are closed by a 90-second heartbeat timeout

Automated checks

  • npm run verify runs four suites:
  • verify:security: authentication and access rules
  • verify:contrast: colour contrast in both themes
  • verify:workbook and verify:department: Excel round-trip and console API

Be ready for these

Likely viva questions

What happens if the AI API goes down during the demo?

Every AI feature has a rule-based fallback. The resume analyzer switches to a 7-factor scorer, interviews use a built-in question bank with keyword grading, and the roadmap uses a template. The app shows a note that AI is unavailable, and the student is never stuck.

How does the video call work without a media server?

WebRTC connects the two browsers directly. Our Socket.io server only relays the setup messages (offer, answer, ICE candidates). STUN servers help each browser find its public address. After that, the media never passes through our server.

How do you stop students cheating on quizzes?

Two layers. In the browser, tab switches and copy/paste are detected and recorded, and three warnings auto-submit the quiz. On the server, the correct answers never leave it and grading happens there, so reading the page source gives nothing away. The browser checks discourage cheating; the server check is what actually prevents it.

Isn’t focus tracking invasive?

It records only whether there was mouse or keyboard activity and whether the tab was visible. It never records what was typed, and it doesn’t use the camera. The student sees exactly the same numbers the teacher sees.

How do you make sure a teacher can’t see another class’s data?

Three checks: protect (are you logged in), authorize (does your role allow this route) and a scope check (authorizeClassroom or canAccessStudent: is this your class or department). The same scope rule is used by the console, analytics and live grid.

Why didn’t you use ChatGPT to answer faculty analytics questions?

An analytics answer must be exact, and an LLM writing database queries can produce a plausible but wrong number, or be tricked into reading data it shouldn’t. We use fixed, tested aggregations selected by pattern matching, which is instant, free and always correct. The trade-off is that fewer question phrasings are understood.

Why MongoDB and not MySQL?

Student records are naturally nested: resume versions, attendance per subject, lists of remarks. Documents store these without many join tables, and MongoDB’s aggregation pipeline handles the analytics. For strict financial-style transactions, a relational database would be the better fit.

How would this scale to 10,000 students?

The REST API is already stateless and runs serverless, so it scales out. The real-time part is the bottleneck: move focus session state into Redis, add the Socket.io Redis adapter so several servers share rooms, put AI calls behind a queue with per-user limits, and add a TURN server for video. The database indexes for department and classroom queries already exist.

Why a readiness score out of 100, and who chose the weights?

One number is easy to track over time and compare across a class. The weights put direct placement skills (quiz, interview, resume, DSA: 15 each) above habits and foundations (10 each). They are editable constants in one file, and a college could adjust them. Missing parts are rescaled rather than counted as zero, so new students aren’t penalised.

Terms used above

Glossary

ATS
Applicant Tracking System: software companies use to filter resumes by keywords before a person reads them.
LLM
Large Language Model. Here, LLaMA 3.3 70B, served by Groq.
Heuristic fallback
A rule-based backup (keyword counting, fixed scores) used when the AI is unavailable.
JWT
JSON Web Token: a signed token the browser sends with each request to prove who the user is.
RBAC
Role-based access control: what a user can do depends on their role (student, faculty, HOD…).
WebRTC
A browser technology for direct peer-to-peer audio and video.
Signaling
Exchanging connection details so two WebRTC peers can find each other. Done here over Socket.io.
STUN / TURN
STUN tells a browser its public address. TURN relays media when a direct connection is impossible.
Heartbeat
A small periodic “I’m still here” message. Here, every 30 s during a study session.
Aggregation pipeline
MongoDB’s way of grouping, filtering and calculating over many documents on the server.
Rate limiting
Capping how many requests one client can make in a time window.
Prompt injection
Hiding instructions in user input to take over an AI’s behaviour.
USN · IA
University Seat Number (student ID) · Internal Assessment marks.
